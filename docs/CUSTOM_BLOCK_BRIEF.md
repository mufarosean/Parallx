# Custom Block Brief — one block type that becomes any block type

Written 2026-08-27. The idea in Mufaro's words: *a widget of sorts — it
retains the rules and physics of blocks, but we allow interaction within
it. The AI then has access to write code to this block, and that code
gets saved and can be refreshed if needed.*

The bet: instead of shipping a mindmap block, a chart block, a diagram
block and a simulation block, ship **one** block whose behaviour is data,
and let the block types be authored — by the AI, by an extension, or by
hand.

---

## Why this shape and not "explorable documents"

A document format is a thing you have to adopt. A block is a thing you
drop into a page you were already writing. Everything the canvas already
does — search, export, flashcard grounding, the block model, undo, drag,
the AI's block tools — keeps working, because from the outside a custom
block is just a block.

The mindmap is the first instance, not a feature. And it is emphatically
**not** the semantic workspace graph: that connects *files*. This
connects *ideas* — the models in a paper, which of them are
over-dispersed, which sit inside the EDF. A picture of the argument, not
a picture of the folder.

---

## The constraint that shapes everything: pages must print

Canvas pages go to PDF. A block whose content only exists while a script
is running cannot participate in that, and "the export is missing the
diagram" is worse than not having the block.

**The contract: every custom block owes a static representation.** On
every settled render, the block hands back an SVG or bitmap snapshot,
stored with the block. Print, PDF export, markdown export, thumbnails and
search all read the snapshot; only an open, focused editor runs the live
version. A block that never produces a snapshot is malformed and the
structural-repair pass should say so.

This also gives the block a free offline story: open a page on a machine
where the runtime is unavailable and you still see the diagram.

---

## The model

The block's attrs carry four things:

- **`kind`** — a name (`concept-map`, `triangle-sim`). Two blocks of the
  same kind share code; the registry dedupes.
- **`code`** — the module that renders and handles interaction. Saved
  with the document, so the block is reproducible and refreshable.
- **`params`** — a typed parameter surface (the same shape widgets
  already use: `WidgetConfigField`). Parameters are what the user pulls,
  and what the AI writes without touching code.
- **`data`** — the content. For a mindmap: the nodes and edges. This is
  the part that belongs to the page.

Splitting `code` from `data` is what makes the mindmap a *mindmap block*
and not a one-off drawing: the same code renders every concept map you
ever make, and the AI edits `data` alone when you ask it to add a node.

### Runtime and sandbox

Precedent exists: dashboard HTML widgets already run as sandboxed
iframes with their own document. Custom blocks should use the same
isolation — code generated by a local model is running inside your notes
application, and it should not be able to reach the workspace except
through an explicit, small API:

- read and write its own `params` and `data` (undoable, through the
  editor's transaction path — never a direct DB write);
- request a snapshot render;
- resolve a link to a page or database row for display.

Nothing else. No filesystem, no network, no arbitrary service access. If
a block needs more, that is an extension, not a block.

### Block physics checklist

From the outside it must behave exactly like an atom block: drag handle,
selection and multi-select, duplicate, delete, copy/paste, undo/redo
fidelity, `blockUnit` resolution, marquee hit-testing, column nesting,
and a markdown-export fallback (snapshot + alt text). The table work of
2026-08-27 is the cautionary tale — a block that looks fine and does not
honour block physics is the kind of thing that survives for months.

## The AI authoring loop

1. *"Make me a concept map of the models in this paper."*
2. The AI writes `data` against an existing `kind` when one fits, or
   writes `code` + `params` + `data` when it does not.
3. It renders; a snapshot is captured; the page is printable immediately.
4. You edit by hand, drag nodes, or ask for a change — and because
   `code` is saved, the block still works with no model available.

The refresh path matters: regenerating `data` must not clobber a layout
you have arranged by hand. Positions belong to the page, not to the
generator.

---

## Decisions (Mufaro's)

**D1 — Is `kind` global or per-page?** Recommendation: a workspace-level
registry with the code embedded in the block as a fallback, so a page
copied elsewhere still renders.

**D2 — Can custom blocks run outside an open editor?** Recommendation:
**no.** Snapshot only. Blocks that compute in the background are a
performance and trust problem with no current use case.

**D3 — Who may author code — AI, extensions, or the user?**
Recommendation: all three, same path, but AI-authored code gets a visible
provenance marker. You should always be able to see that a block was
model-written.

**D4 — First instance.** Recommendation: the **concept map**, built as a
custom block from day one rather than as a bespoke feature — it is the
one you actually want, and it proves the model end to end (interaction,
snapshot, AI-written `data`, hand-editable layout).

---

## Execution sketch

1. Node type, attrs, and the snapshot contract; a hand-written `kind`
   rendering a static SVG. Print/export path proven first.
2. Sandbox host and the small API. Interaction inside the frame.
3. Parameter surface reusing the widget config field types.
4. The concept map as the first real `kind`.
5. AI authoring: tools to write `data`, then `code`, with provenance.
6. Registry, dedupe, refresh-without-clobbering-layout.

## Risks

- **Printing is the acceptance test**, not an afterthought. If step 1
  does not end with a PDF containing the diagram, stop.
- **Sandbox escape.** Model-written code in a notes app; the API is the
  security boundary and it should stay embarrassingly small.
- **Kind sprawl.** Ten near-identical `concept-map-2` kinds is the
  failure mode. Dedupe and naming matter earlier than they seem to.
- **This is not a plugin system.** Anything needing services, network or
  files is an extension. Keep the line bright.
